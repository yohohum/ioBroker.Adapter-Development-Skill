# Этап 1. Сбор требований и анализ устройства

## Цель

До генерации кода получить проверяемую спецификацию устройства/сервиса и понять, что именно должен делать адаптер.

## 1. Входные данные

Собери, если доступны:

- производитель, семейство и точная модель устройства;
- аппаратная ревизия и версия firmware;
- официальная документация, API reference, protocol specification;
- способ подключения (LAN, cloud, serial, MQTT, BLE через gateway и т. п.);
- тип аутентификации и TLS;
- известные ограничения: rate limits, concurrency, command timeout;
- перечень функций устройства, читаемых параметров и управляющих команд;
- пример запросов/ответов, события, коды ошибок;
- какие модели должны поддерживаться и какие не поддерживаются;
- требования пользователя к discovery, multi-instance, multi-device, Admin UI и диагностике.

Не проси секреты у пользователя без необходимости. Для тестов используй фиктивные значения.

## 2. Источники

Приоритет:

1. Официальный сайт производителя и спецификация.
2. Официальный SDK/API и примеры производителя.
3. Официальное описание firmware/API version.
4. Логи/захваты пользователя, предварительно очищенные от credentials.
5. Репозитории других open-source проектов — только как вторичный источник и с проверкой лицензии.

Если API не документирован, укажи это; не представляй reverse engineering как официальный контракт. Не копируй код из чужого репозитория без проверки лицензии и авторских ограничений.

## 3. Матрица функций

Создай таблицу:

| Capability | Read/Write | Протокольная операция | Ответ/подтверждение | Объект ioBroker | Ошибки/ограничения |
|---|---|---|---|---|---|

Каждая команда должна иметь определённый тип, диапазон, единицы, timeout, повторяемость/idempotency и способ подтверждения.

## 4. Матрица совместимости

Зафиксируй:

- минимальный и рекомендуемый js-controller;
- минимальный и рекомендуемый Admin;
- Node.js диапазон из реальных `engines`/совместимости;
- версии firmware/device API;
- OS/architecture, если есть ограничения;
- режимы адаптера (daemon/schedule/once/none), обоснованные сценарием.

Не используй случайные современные версии в качестве minimum. Проверяй совместимость по официальному js-controller README и реально используемым API.

## 5. Риски

Особо зафиксируй:

- операции, способные повредить оборудование/данные;
- операции с внешними платежами/облачными лимитами;
- возможность утечки секрета;
- отсутствие sandbox/test device;
- неопределённость в семантике ACK;
- опасность повторного выполнения команд;
- обратную совместимость старых native config и object IDs.

## Критерии завершения

- [ ] Есть список поддерживаемых моделей/версий.
- [ ] Все функции классифицированы read/write.
- [ ] Протокольные запросы/ответы и ошибки описаны или отмечены как неизвестные.
- [ ] Выбраны транспорт и auth flow.
- [ ] Определены минимальные версии Node/controller/Admin с источниками.
- [ ] Неопределённости и риски явно переданы пользователю.

**Не переходи к архитектуре**, пока неизвестные данные не будут либо подтверждены, либо явно приняты как ограничения первой версии.
