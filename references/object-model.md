# Объектная модель ioBroker

## 1. Официальный контракт

Источник истины:

- [Object types](https://github.com/ioBroker/ioBroker.docs/blob/master/docs/en/dev/objectsschema.md)
- [State roles](https://github.com/ioBroker/ioBroker.docs/blob/master/docs/en/dev/stateroles.md)
- [Controller schema](https://github.com/ioBroker/ioBroker.js-controller/tree/master/schemas)

При реализации сверяй допустимые поля с актуальными схемами. Примеры ниже — проектные правила и не заменяют JSON Schema.

## 2. Иерархия

Используй дерево `device` → `channel` → `state`, когда оно соответствует реальному устройству:

```text
adapter.0
└── deviceId                 (type: device)
    └── info                 (type: channel)
        ├── name             (type: state)
        ├── reachable        (type: state)
        └── firmware         (type: state)
    └── controls             (type: channel)
        ├── power            (type: state)
        └── brightness       (type: state)
```

Не создавай бессмысленные уровни и не используй `device`/`channel` как обязательный шаблон для любого сервиса. ID должны быть стабильными, безопасными для ioBroker и воспроизводимыми после перезапуска. Разделяй идентификатор устройства и отображаемое имя: имя может измениться, ID — нет.

## 3. Требования к state

Каждый объект `type: "state"` должен содержать корректные свойства `common`, в частности:

- `name` — понятное имя (строка или локализованное описание в поддерживаемом формате);
- `type` — реальный тип значения: `boolean`, `number`, `string` или допустимый актуальной схемой тип;
- `role` — максимально конкретная семантическая роль из `STATE_ROLES.md`;
- `read` — может ли пользователь/клиент читать значение;
- `write` — может ли пользователь/клиент отправлять команду;
- `unit`, `min`, `max`, `states`, `def`, `desc` — когда применимо.

Не устанавливай `read: true, write: true` по умолчанию для всех datapoints. Решение определяется протоколом и семантикой: измеренная температура часто read-only, setpoint — read-write, команда — write-only или read/write в зависимости от роли и реального поведения устройства.

## 4. Роли

- Для чтения используй соответствующую sensor/indicator/value роль.
- Для управления используй operative roles (`switch`, `level.*`, `button` и т. п.), наиболее конкретную из официального списка.
- Для `indicator` официальная документация указывает boolean и read-only (`common.type=boolean`, `common.write=false`). Не используй `indicator` для управления.
- Роль `button` имеет особую семантику; проверь её текущие требования в `STATE_ROLES.md` и repochecker. На момент текущей проверки repochecker отдельно проверяет `button` с `read:false`, `write:true`.
- Не придумывай собственные роли без согласования с ioBroker; в спорных случаях подними вопрос/Issue в официальном проекте.

## 5. ACK и состояния

`ack=false` означает команду, инициированную клиентом/пользователем. `ack=true` означает подтверждённое/фактическое состояние.

Рекомендуемая логика write:

1. Получить `stateChange`.
2. Игнорировать `null` и подтверждённые события (`ack=true`), если они не нужны для другой логики.
3. Проверить тип, диапазон и состояние соединения.
4. Выполнить команду по протоколу.
5. Обработать ответ/ошибку и при необходимости запросить readback.
6. Только после фактического подтверждения обновить состояние с `ack:true`.
7. При ошибке залогировать безопасное сообщение; не имитировать успех. Состояние фактического устройства не должно становиться равным желаемой команде без подтверждения.

Некоторые протоколы подтверждают только приём команды, а не физическое достижение состояния. В этом случае документируй семантику ACK отдельно и обновляй фактические datapoints по телеметрии/readback.

## 6. Удаление и миграция

При обновлении схемы:

- не меняй ID существующих объектов без миграционного плана;
- не удаляй пользовательские объекты и состояния, которыми управляют другие адаптеры;
- удаляй только объекты, которые адаптер однозначно считает своими;
- при переименовании/перестройке поддержи перенос значений/настроек, если требуется;
- учитывай несколько экземпляров адаптера и разные устройства;
- тестируй обновление с предыдущей опубликованной версией на тестовой базе.

## 7. Идентификаторы

Создай одну функцию нормализации идентификатора и тесты для неё. Учитывай пробелы, точки, слеши, Unicode, пустые значения и совпадения после нормализации. Не допускай коллизий двух разных физических устройств; если нормализация может приводить к коллизии, добавляй стабильный безопасный суффикс или используй исходный уникальный ID в обратимо безопасной форме.

## 8. Обязательная проверка

Для всех созданных state:

- проверить существование `common.role`;
- проверить соответствие роли типу, read/write;
- открыть актуальный `STATE_ROLES.md`;
- запустить `@iobroker/testing` package tests;
- запустить `@iobroker/repochecker`;
- сформировать OBJECTDUMP и просмотреть его структуру.
